# 0EN セキュリティ基本方針 v0.1

作成日：2026-10-09  
対象：0EN WORK の公開LP、企業向け入力・管理PoC、求職者向けPoC  
位置づけ：DB・認証・本番公開の前に確認する設計方針。法的助言や本番環境の監査報告ではない。

## 1. この文書で固定すること

0ENは、機能を増やす前に「誰が何を変更できるか」「何を保存しないか」「攻撃や事故が起きたときに止めて戻せるか」を決める。

- 企業アカウント、求人原稿、掲載状態は、企業ごとの認証・認可が成立するまで本番データとして扱わない。
- 求職者アカウントを作らない。応募者の氏名、メールアドレス、電話番号、履歴書、職務経歴書を0EN上で取得・保存しない。
- 応募は企業が指定する外部のメール、電話、自社フォームなどへ渡す。0ENは応募内容を受け取らない。
- DBを導入しても、ブラウザからDBへ直接接続させない。認証済みAPI、入力検証、認可、監査ログを経由させる。
- APIトークン、DB接続情報、署名鍵、管理者用情報をリポジトリ、HTML、クライアントJavaScriptへ保存しない。
- 公開系と企業管理系を分離し、公開求人ページから管理操作へ到達できない構成にする。
- 企業登録、ログイン、求人作成、掲載、問い合わせ、ファイル取込には、レート制限と自動化対策を適用する。

## 2. 守る対象

| 対象 | 守る内容 | 0ENでの扱い |
|---|---|---|
| 企業アカウント | 会社情報、担当者情報、ログイン状態 | DB導入前に認証・認可方式を確定する |
| 求人原稿 | 原稿本文、給与、勤務地、掲載状態、履歴 | 企業間の読み書きを分離する |
| 公開求人 | 改ざんされていない公開内容、公開URL | 公開用の読み取り経路を管理系から分離する |
| 応募者情報 | 氏名、連絡先、履歴書等 | 原則として0ENで取得・保存しない |
| 秘密情報 | APIトークン、DB接続情報、署名鍵 | 環境変数・Secretsだけで管理する |
| 運用情報 | 監査ログ、停止履歴、バックアップ | 保存期間と閲覧権限を後続設計で定める |

## 3. 想定する脅威

### 3.1 未認証の攻撃者・BOT

- 企業登録や求人投稿を大量に行う。
- ログイン試行、問い合わせ、ファイル取込を自動化する。
- 公開求人へフィッシング、詐欺、危険な外部URLを登録する。
- 公開ページをクロールしてサービス負荷を高める。

### 3.2 悪意のある登録企業

- 別企業の求人を閲覧・編集・停止する。
- 求人本文にスクリプト、外部誘導、誤認を招く表現を埋め込む。
- 掲載停止後に複製や再登録で求人を復活させる。

### 3.3 正常利用中の事故

- 企業担当者が誤った給与・勤務地・応募先を公開する。
- インポートしたExcel、CSV、TXTの表記や数式セルを誤って反映する。
- 削除・停止・更新の履歴が残らず、元に戻せない。

### 3.4 依存関係・運用環境

- JavaScriptライブラリやファイル解析処理の脆弱性を利用される。
- APIキーやCloudflare設定がGit履歴・ログ・クライアントへ漏れる。
- 障害や侵害後にバックアップから復旧できない。

## 4. 現状PoCの確認結果（読み取り専用レビュー）

### 良い前提

- 公開LPは静的HTML/CSSで、現時点ではDB・認証・本番求人投稿APIを持たない。
- Cloudflare Workers AIの認証情報は環境変数から読み込む実装で、リポジトリへ値を書き込む処理は確認できない。
- `.gitignore`で`.env`、`.dev.vars`、Wranglerのローカル状態を除外している。
- 求職者PoCは応募者情報を入力する画面を持たず、応募先を外部へ渡す設計になっている。
- iframe間のPoC通信では`origin`と`source`を確認する処理がある。
- 外部応募URLは`http`/`https`だけを許可し、`javascript:`やURL内の認証情報を拒否している。
- インポート画面では値を表示用エスケープ関数に通し、Excelの数式セルを反映しない扱いにしている。

### 本番前に解消が必要な点

| 優先度 | 確認事項 | 現状 | 本番前の要求 |
|---|---|---|---|
| P0 | 認証・認可 | PoCには企業アカウント境界がない | 企業IDをサーバー側セッションから確定し、全求人操作で所有者認可を行う |
| P0 | DB/API境界 | DB未接続。localStorage中心 | DB直接接続を禁止し、APIごとに認証・認可・入力検証を行う |
| P0 | 秘密情報 | 環境変数方式はあるが、運用権限は未確定 | 最小権限トークン、Secrets管理、ローテーション、漏えい時の失効手順を定める |
| P1 | XSS | `innerHTML`を使う箇所がある。主要表示にはエスケープ処理がある | 表示経路をエスケープ関数へ統一し、HTMLを許可する場合はサニタイズ方針を別途定める |
| P1 | 外部URL | PoCではプロトコル等を検証 | 本番では保存時・表示時の二重検証、危険URLの拒否、外部遷移の明示を行う |
| P1 | ファイル取込 | ブラウザ内でサイズ・行数・列数を制限 | サーバー側でもサイズ、展開後容量、行列数、処理時間を制限し、数式・マクロを実行しない |
| P1 | レート制限 | PoCでは未実装 | 登録、ログイン、投稿、編集、問い合わせ、取込、共有URL発行に適用する |
| P1 | 監査・復旧 | PoCはlocalStorageで、監査ログ・バックアップなし | 作成者、更新者、公開・停止・削除、認証失敗、管理操作を記録し復旧手順を試験する |
| P2 | 依存関係 | 依存を最小化し、一部ライブラリを同梱 | 採用バージョン、ライセンス、脆弱性通知、更新担当を固定する |
| P2 | 公開情報 | PoC用の連絡先・サンプル求人が存在 | 本番では架空データと実データを分離し、noindexや公開範囲を確認する |

なお、リポジトリには画像生成PoCの`__pycache__`成果物が追跡されている。秘密情報ではないが、生成物をGit管理しない運用へ整理する候補として記録する。

## 5. DB実装前の必須ゲート

次の項目が決まるまで、企業アカウントと求人DBの本実装を開始しない。

1. 認証方式、セッション有効期限、ログアウト、メール変更、アカウント停止の仕様。
2. 企業、メンバー、求人、Revision、PublicationCycleの所有関係と操作権限表。
3. 公開読み取りAPIと管理APIの分離、CSRF対策、入力検証、エラー応答の方針。
4. 登録・ログイン・投稿・問い合わせ・ファイル取込のレート制限とBOT対策。
5. 求人の通報、停止、削除、復旧、侵害時の緊急停止手順。
6. ログ、バックアップ、保存期間、復旧テスト、秘密情報のローテーション手順。
7. 脅威シナリオを使った受入テスト（他社求人へのアクセス、XSS、危険URL、大量投稿、権限外操作）。

## 6. 今回の判断

この文書の作成ではコード、DB、認証、公開設定を変更しない。PoCのlocalStorageや固定サンプルは、機密情報を保存しない検証用途に限る。

本番実装へ進む際は、この文書を更新してから最小単位の認証・認可を実装し、テストで企業間の分離を確認する。機能追加の便利さより、誤公開・越権操作・不要な個人情報の保持を避けることを優先する。
