# WORK関連付け・グラフ構想（仮案 v0.1）

作成日: 2026-10-18

## 目的

0EN上のWORKを単なる一覧・カテゴリとして蓄積するのではなく、WORK同士の「つながり」を一級データとして扱う。

ただし、利用者に複雑なグラフ作成や関係分類を要求しない。自分のWORKを紹介する自然な操作の延長として関連付けを行い、その結果として0EN全体にWORKの関係グラフが育つ設計を目指す。

## 基本方針

利用者に「WORK同士の関係を定義してください」と要求すると難しい。

そこで、関連付けの起点を **自分のWORK** にする。

例：

1. 自分のWORKを紹介する
2. 紹介ページを作る
3. 「このWORKに関連するものはありますか？」と案内する
4. 0EN内のWORKを検索する
5. 「関連付ける」を選ぶ
6. 公開する

関連付けは任意とし、関連WORKがなくても公開できる。

## 初期段階では関係種別を必須にしない

初期実装では、次のような細かな分類を入力必須にしない。

- 使っている
- 参考にした
- 一緒に使える
- 派生した
- おすすめしたい

まずは単純に、

`WORK A → related → WORK B`

という関連だけを保存できればよい。

実際の利用状況を見て必要性が確認できた段階で、関係種別を追加する。

## 片方向と相互関連

Aさんが自分のWORK AからWORK Bを関連付けた場合、まず片方向の関係として扱う。

`WORK A → WORK B`

WORK Bの管理者もWORK Aを関連付けた場合、双方から関係が成立する。

`WORK A ↔ WORK B`

これは、従来Webの相互リンク文化をWORK単位へ拡張したものとして扱える。

- 片方向：紹介・関連付け
- 双方向：相互につながったWORK

相互関係の具体的な表示名称は今後検討する。

## グラフは結果として生成される

利用者にObsidianのようなグラフを直接編集させることを初期要件にしない。

各利用者が自分のWORKへ関連WORKを追加していくことで、裏側では自然にグラフが形成される。

例：

```text
           WORK B
          /
WORK D - WORK A - WORK C
          \
           WORK E
```

利用者は「グラフを作っている」のではなく、自分のWORKと関係があるWORKを選んでいるだけでよい。

## 将来のグラフ表示

関連データが蓄積した段階で「つながりを見る」表示を追加できる。

初期のグラフ表示は全WORKを一度に描画せず、現在見ているWORKを中心に10～20ノード程度のローカルグラフを表示する。

ノードを選択すると、そのWORKを中心として周辺を再描画する「歩いていくグラフ」を想定する。

これにより、巨大な毛玉状グラフを避け、スマートフォンでも探索に使えるUIを目指す。

## 個人Hubとの関係

個人Hubを単なるお気に入り一覧やまとめページとして固定しない。

自分が紹介したWORKと、それぞれの関連WORK、その先にある他者のWORK・Hubがつながることで、結果として「その人のWORKの地図」が形成される構造を検討する。

同じWORKが複数の人のHubやWORKから関連付けられれば、そのWORKを介して人・Hub同士も間接的につながる。

## 行動から生まれる関連性

将来的には、明示的な関連付けだけでなく、多くの利用者が同じWORK群を関連付けている事実も補助的な関係情報として利用できる。

例：

- 「このWORKと一緒に紹介されることが多いWORK」
- 「複数のHubで一緒に登場するWORK」

これはAI推薦を必須にせず、実際の利用者の行動から関係性を発見する仕組みにできる。

ただし初期実装では必須としない。

## 実装段階案

### Phase 1

WORK詳細から関連WORKを手動登録できる。グラフ表示は行わない。

### Phase 2

自分のWORK群と関連WORKをHub上で確認できる。

### Phase 3

「つながりを見る」でローカルグラフを表示する。

### Phase 4

他者のWORK・Hubへグラフ上から横断できる。

### Phase 5

外部Webとの相互リンク情報も含め、0EN内外のつながりを探索できるようにする。

## DB設計上の考え方

専用グラフDBを初期から必須にしない。

通常のリレーショナルDBでも、例えば以下のような関係テーブルを持てば開始できる。

```text
work_links
- id
- from_work_id
- to_work_id
- relation_type (初期は related 固定でもよい)
- created_at
```

WORK数・エッジ数・探索クエリが実際に増えて問題になった段階で、グラフDB等を検討する。

## 設計原則

> 利用者にグラフを作らせない。自分のWORKを関連付けてもらう。その積み重ねが0ENのグラフになる。

0ENの価値を「大量のページを所有すること」だけに置かず、誰かが作ったWORKと別のWORKの間に生まれた関係性を蓄積・探索できることへ広げていく。
