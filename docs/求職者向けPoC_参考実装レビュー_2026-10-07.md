# 求職者向けPoC 参考実装レビュー

確認日：2026-10-07。対象は指定4リポジトリの取得時点のコード。fork・依存インストール・起動・コード導入は行っていない。静的レビューであり、レスポンシブ・アクセシビリティ・SEOの実機合格を保証しない。既存0ENスキーマ・LP・PoCを変更しない。

## 1. 結論

全体をベースとして導入せず、0ENの既存Job／Revision／PublicationCycleから求職者向け表示を生成する独自PoCを推奨する。Startupkitから表示・安全処理の分離、jjtsouからURL検索・ページングを参考にする。Oluwamightyは小さな画面構成の参考、startups-boardは将来の検索API・D1設計の参考に留める。
応募者アカウント、応募フォーム、履歴書、応募管理、ATS、AI、課金、有料順位、ランキングは採用しない。求人の収集・外部媒体への自動アクセスも対象外。

## 3. 各候補のコードレビュー

### Oluwamighty：シンプルな一周の参考

確認：`src/app/jobs/page.tsx`、`src/app/jobs/[id]/page.tsx`、`src/app/components/SearchBar.tsx`、`FilterBar.tsx`。
- 一覧は求人名・会社・地域・カテゴリ・雇用形態をカード化。1／2／3列のCSS分岐と空結果から条件解除への入口がある。給与が一覧にないので、0ENでは給与を優先して加える。
- 検索はURLのsearch、category、type。500ms debounceで更新。ただし検索欄はURLから初期化した後の戻る／進むとの同期が明示されず、入力中のpushで履歴を増やす。0ENでは検索実行時push、入力中の補助更新replace等を独自設計する。
- 詳細と外部Applyリンクあり。ただしjob.urlは元求人のURLで、必ず直接応募先とは限らない。0ENでは企業が指定した応募方法とリンクだけを使う。
- 詳細は全件APIを取得してidを探索し、本文HTMLを直接描画する。0ENの1件取得・公開状態チェック・安全なテキスト表示へ置き換える。
- JobPosting実装は確認できない。`JobCard.tsx`は取得時点で空で、実際のカードは一覧ページ内に実装されている。コンポーネント名だけで流用候補としない。

### Startupkit：表示とデータ境界の分離が最も参考になる

確認：`components/job-card.tsx`、`job-filters.tsx`、`salary.tsx`、`app/jobs/[token]/page.tsx`、`lib/jobs.ts`、`sanitize.ts`、`jsonld.ts`。
- カードは職種・勤務地・雇用形態・給与・掲載日をまとめ、狭い画面では縦配置。データ取得／表示整形／カードを分離する構造が良い。単一企業の部門表示は0ENの募集企業名・勤務地へ置き換える。
- URLフィルタはdepartment／location／employment_type／remote。条件変更時pageを削除し、現在の値が候補一覧にない場合も選択肢へ保持する。選択肢が空のときの非表示も参考になる。ただし多企業求人の20職種分類へ合わせる必要がある。
- 詳細には上部・下部のApply、受付終了表示、metadata、JSON-LD、データ境界のsanitize-htmlがある。通常本文のサニタイズとJSON-LDのscript終端対策を別処理にする点は採用候補。
- API・トラッキング・応募フォーム・talent-poolにKit依存がある。0ENに不要なので丸ごと導入しない。
- JSON-LDは会社を環境変数から取得し、directApply=trueを固定、salaryをbaseSalaryへ変換。validThroughはこの生成関数にない。0ENでは企業ごとの会社、実際の応募導線、給与の意味、PublicationCycleの期限に対応させる。
- salary表示は上下限が片側だけの状態も扱うが、英語・compact表記。日本円の「月給250,000円～」等へ変える。契約社員を一律CONTRACTORへ変換することも、日本の有期雇用と業務委託の区別を検討してから行う。

### startups-board：Cloudflareの検索基盤参考、PoCベースには大きすぎる

確認：`web/app/jobs.ts`、`jobs-explorer.tsx`、`jobs-query.ts`、`api/jobs/route.ts`、`cloudflare/wrangler.jsonc`。
- Workers・D1・R2・Queuesを組み合わせる求人収集型。正規化型に企業・国・地域・職種群・雇用形態等を持つが、0ENのセルフ投稿スキーマの置き換えには使わない。
- 条件→URLとURL→条件を分離。選択済みチップ・条件解除・検索リクエスト取消・検索条件に対応するページカーソルを扱う。
- D1の全文検索／条件の組み合わせ、APIページングと検索結果の競合防止が将来参考になる。大量求人向けの最適化は数十求人PoCには不要。
- UI／クエリは大規模。全世界・ATSソース別・企業保存等の機能を持ち込まない。詳細画面の0EN用部品、JobPostingの実装としては今回の閲覧対象で採用候補を確認していない。

### jjtsou：URL・検索・ページングの設計参考

確認：`src/app/[locale]/page.tsx`、`src/lib/seo.ts`、`components/jobs/JobSearchForm/utils.ts`、`JobPagination/utils.ts`、`JobCard/JobCard.tsx`。
- q／location／category／pageをURLで保持。検索時にpageを削除し、ページ移動では条件を保持する。小さな純粋関数と関連テストの切り分けが参考になる。
- SSR取得、metadata／canonical／多言語の仕組みあり。ただしSEOユーティリティは不正値・配列の検証まで十分に行うものではない。0ENでは許容する値とページ番号を入口で検証する。
- カードは会社・地域・分類・本文抜粋・掲載日。給与・雇用形態・詳細リンクはこのカードで確認できない。ルート一覧でも個別求人詳細ページを確認できない。紹介の「一覧→詳細→Applyまで」の根拠としては不足。
- Chakra・next-intl等は0ENの軽量PoCに追加しない。検索状態・ページングの発想だけ採用する。JobPosting実装はsrc内で未確認。

## 4. 0ENへ採用するパターン

| 領域 | 採用する考え方 | 0ENでの調整 |
|---|---|---|
| 一覧カード | 職種、会社、勤務地、雇用形態、給与、掲載日を同じ順で配置 | 給与の単一／範囲／下限のみを維持。最初は情報を比較しやすい縦一覧を推奨、写真やロゴを必須にしない |
| URL検索 | 条件をURLへ持ち、再表示・戻る・共有で復元 | q、location、occupation、employment、page。表示ラベルと内部値を分離。空・未知enum・不正pageを検証。条件変更でpageを1へ |
| 条件保持 | ページ移動と詳細から戻る時に条件を保持 | 詳細の戻るリンクに検証済み検索条件を渡す。条件全解除と個別解除を区別 |
| フィルタ | 選択中の値を保持、検索0件から解除可能 | 勤務地・職種・雇用形態を優先。月給と時給を混ぜた給与比較や勝手な月額換算はしない |
| 詳細 | 主要条件→仕事内容→勤務・休日→待遇・試用→応募方法 | 既存の構造化項目と原文を表示用に整形。問い合わせと応募を分離 |
| 応募導線 | 受付終了時のボタン停止、指定先へ誘導 | 外部URL／メール／電話を企業が指定した場合だけ。URLschemeを検証。応募先未指定を問い合わせ先で推測補完しない |
| 公開対象 | 一覧・詳細・検索で同じ公開判定 | 有効なPublicationCycleの対象Revisionのみ。完成・未掲載は除外、期限切れ・停止は詳細URLでも除外。編集中の最新版を公開版へ無条件に上書きしない |
| レスポンシブ | 主要情報の順を保ち、狭い画面は縦配置 | フィルタを折りたたんでも適用件数を見せる。横スクロール前提にしない |
| アクセシビリティ | label、見出し階層、通常リンク、フォーカス、結果・空状態 | スマホ・キーボード・日本語長文・0件を実機で検証する。クラス名やaria属性があるだけで合格としない |

URLはPoCでも検索状態の正本として扱えるが、ブラウザ内だけの一時求人は他端末へ共有されない。URL共有可能と永続データ共有可能を混同しない。

## 5. SEO／JobPosting：そのままコピーしない

[Google公式 JobPosting仕様](https://developers.google.com/search/docs/appearance/structured-data/job-posting)を確認した。本番時に以下を設計する。
- JobPostingは1求人の詳細ページだけに配置し、一覧や検索結果には付けない。
- title／description／hiringOrganization／jobLocation／datePosted等は表示内容と同じ公開版から生成する。会社は求人の募集企業、0EN運営ではない。
- validThroughは掲載回の期限へ対応。終了時は期限・削除／404・410・構造化データ除去等、公式の終了方法と公開ポリシーを合わせる。本文だけ停止して有効なJobPostingを残さない。
- 総支給額しかない値を基本給と推定してbaseSalaryへ入れない。基本給が確認済みで出力要件を満たす場合の扱いを別途確認。下限のみのmaxは生成しない。
- directApply=trueを固定しない。外部リンクがあるだけで直接応募要件を満たすとは断定しない。
- filter URLの共有とindex許可は別。すべての組み合わせをindex対象にするcanonical方針を無条件で採用しない。
- ブラウザPoCでは表示対応とJSON-LD生成の机上テストまで。本番のSSR・クロール・Rich Results Test・検索掲載は別検証。生成すればGoogle求人検索に必ず出るというものではない。

## 6. 次のPoC範囲

統合トップ（検索が主役、企業入口はヘッダー）→求人一覧／条件検索→求人詳細→企業指定の応募方法を確認、まで。既存企業ポータルの模擬掲載・停止と表示を一周させる。データは既存項目とPublicationCycleから読み、参照専用の表示変換層を作る。新しい求人スキーマ・Next.js導入・DB・認証・AI・応募フォームは今回確定しない。
次版で試す条件：完成・未掲載を出さない、停止・期限切れを出さない、公開中に新Revisionを編集しても公開版が勝手に変わらない、給与範囲と以上、検索URL復元、詳細から条件を維持して戻る、応募先なしの誤誘導防止。

## 7. 調査の限界・要確認

コード静的レビューのみで4プロジェクトを起動していない。API応答・実サイトのアクセシビリティ・SEO・本番性能は未検証。ライセンスは固定コミットのファイルから確認、依存とロゴ・外部求人データの権利は別。JobHive／OpenATSは今回4候補の抽出対象から除外し、コードレビューしていない。
現0ENポータルPoCはスナップショットが原稿版へ残るが、最初の仮データや複製の版には完全な本文スナップショットがない。求職者側を接続する際は公開版参照のテスト用データを整える必要がある。これは次の修正候補であり、今回のレビューでは既存PoCを変更しない。
