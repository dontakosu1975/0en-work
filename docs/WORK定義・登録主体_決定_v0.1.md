# WORK定義・登録主体（決定 v0.1）

更新: 2026-10-18

## 結論

0ENにおけるWORKは、作品・商品・サービス・仕事だけを指すものではない。

> **WORKとは、自分や自分たちが取り組んでいること。**

完成している必要も、販売されている必要も、職業である必要もない。

メイク、ネイル、料理、ものづくり、お店、新メニュー、求人、地域活動、情報発信、趣味、アプリ開発など、誰かが「やっていること」はWORKになり得る。

> **WORKは特別な人だけが持つものではない。誰にでも、何かしらのWORKがある。**

---

## 1. WORKは「何を作ったか」だけではない

0ENは完成品の作品投稿サイトではない。

WORKとして扱える例:

- 自分なりのメイク方法を試して紹介している
- ネイルデザインを考えている
- 趣味で工作している
- アプリを開発している
- 店を運営している
- 新メニューを作っている
- スタッフを募集している
- 地域活動を続けている
- Xで地元のおいしいラーメン店を紹介している
- ブログで便利な道具を紹介している
- GitHubでツールを公開している

重要なのは対象物の所有権ではなく、**登録者側がその「取り組み」の当事者であること**。

---

## 2. 第三者紹介との境界

初期版では、他者のWORKそのものを第三者が代理登録する機能は持たない。

例:

```text
× 「○○ラーメン店」を、無関係な第三者が店のWORKとして代理登録する
```

一方、他人・店・作品・場所などを紹介する活動そのものが自分の取り組みであれば、それは自分のWORKとして登録できる。

```text
○ 「地元のおいしいラーメン店をXで紹介しています」
   → 自分自身の情報発信活動なのでWORK
```

したがって初期版の原則は、

> **自分・自社・自分たちが当事者として取り組んでいるWORKを紹介する。**

とする。

これは「自分が所有するものしか掲載できない」という意味ではない。

---

## 3. 個人・店舗・企業・団体を同じ考え方で扱う

### 個人

```text
私のメイク方法
ネイルデザイン
DIYで棚を作る
自作アプリを開発する
バンド活動をする
地元のお店をSNSで紹介する
```

### 店舗

```text
お店を運営する
秋の新メニューを始める
イベントを開催する
スタッフを募集する
店内を改装する
```

### 企業・団体

```text
新製品を開発する
採用活動をする
求人を出す
地域イベントを行う
社内ツールを作る
啓発活動を行う
```

これらはすべてWORKとして同じ基盤へ載せられる。

---

## 4. 「登録した人」と「取り組んでいる主体」は分けて考える

会社・店舗・団体では、実際にフォームを操作する担当者と、WORKの主体が異なる。

例:

```text
登録操作をした人: 山田さん
取り組みの主体:   ○○株式会社
WORK:             ホールスタッフを募集しています
```

したがってデータ設計では、少なくとも概念上、

- 誰が登録・管理しているか
- 誰／どの組織の取り組みか

を分離できる構造にする。

`owner` のような「所有者」を前提とする用語は、WORKの意味と合わない可能性があるため慎重に使用する。

初期スキーマでは `created_by` / `managed_by` と `actor` 等の表現を候補とするが、正式なフィールド名はWORK共通スキーマ v0.1で確定する。

---

## 5. 第三者による代理登録は将来拡張

将来的には、本人以外が他者のWORKを紹介する仕組みを追加する可能性は残す。

その場合に必要となり得るもの:

- 本人による引き取り
- 本人確認
- 紹介者とWORK主体の区別
- 掲載拒否
- 権利・内容に関する通報
- 管理権限の移管

ただし、これらは初期実装の対象外とする。

初期版では代理登録を排除することで、WORK共通スキーマと公開フローを単純に保つ。

---

## 6. WORKの定義をUIへどう見せるか

内部では `WORK` を共通概念として使用するが、初めて訪れた利用者へいきなり抽象概念を要求しない。

説明例:

> **WORK（ワーク）とは、あなたが取り組んでいること。**
>
> 仕事だけではありません。趣味でも、お店でも、ものづくりでも、情報発信でも、求人でも。あなたが「やっていること」を0ENではWORKと呼びます。

登録導線では「WORKを所有していますか？」ではなく、

- あなたのWORKを紹介する
- あなたが取り組んでいることを紹介する

などの表現を優先する。

---

## 7. WORK共通スキーマへの要求

次に作成するWORK共通スキーマ v0.1では、本決定を前提とする。

最低限考慮するもの:

```yaml
work:
  id:
  slug:
  type:
  title:
  summary:
  body:

  created_by:      # 登録・管理するアカウント

  actor:           # この取り組みを行っている主体
    type:          # person / organization 等
    name:

  publication_status:
  activity_status:
  categories:
  images:
  external_links:
  created_at:
  updated_at:
  published_at:
```

これは概念例であり、正式なDBフィールド定義ではない。

---

## 設計原則

> **0ENが扱うのは「何を持っているか」ではなく、「何に取り組んでいるか」。**

> **誰か・何かを紹介すること自体も、その人が継続して取り組んでいるならWORKになり得る。**

> **初期版では、自分・自社・自分たちが当事者であるWORKだけを登録する。第三者による他者WORKの代理登録は扱わない。**
